# Backend prompt: надёжный приём команд и результатов от San Diego Agent

## Цель

Реализовать backend-контракт так, чтобы Roblox-агент San Diego мог **гарантированно** доставлять результаты выполнения команд, а backend мог отличать живую команду от зависшей.

## Базовые endpoint'ы

### 1. Выдача команды — long polling

```
GET /commands/next?nickname={nickname}&long_poll=true&timeout=30
```

Query-параметры:
- `nickname` — обязательный.
- `long_poll=true` — обязательный.
- `timeout` — максимальное время удержания соединения в секундах, 1..300 (рекомендуется 30).

Поведение:
- Удерживать HTTP-соединение до появления команды в статусе `pending` или до таймаута.
- При таймауте вернуть HTTP 200 с телом `null` (или HTTP 204).
- Как только соединение закрывается, агент тут же открывает новый long poll.
- Выдавать **ровно одну** команду за запрос. Команда переходит в статус `in_progress` и должна содержать поле `taken_at`.

### 2. Приём результата

```
POST /commands/{id}/result
```

Тело:
```json
{
  "result": "строка с JSON или текстовым описанием",
  "status": "completed" | "error" | "cancelled"
}
```

Требования:
- `status` — обязательно.
- `result` — строка, опционально.
- **Идемпотентность**: повторный `POST /commands/{id}/result` с тем же `id` не должен создавать дубликатов, перезаписывать более новые статусы или вызывать побочные эффекты. HTTP-ответ должен быть 2xx, чтобы агент считал доставку успешной.
- После успешного приёма результат переводит команду в финальный статус (`completed`/`error`/`cancelled`).

### 3. Приём промежуточного статуса

```
POST /commands/{id}/status
```

Тело:
```json
{
  "status": "in_progress" | "completed" | "error" | "cancelled" | "declined",
  "message": "optional human-readable message"
}
```

Требования:
- `status` — обязательно.
- `message` — опционально, строка.
- **Идемпотентность**: повторные `POST /commands/{id}/status` не должны ломать состояние. Например, `in_progress` с `message: "heartbeat"` должен обновлять `updated_at`, но не переводить финальную команду обратно в `in_progress`.
- Финальный статус (`completed`/`error`/`cancelled`) не должен быть перезаписан более поздним `in_progress`.

## Жизненный цикл с надёжной доставкой

1. **Выдача**: агент получает команду через `GET /commands/next`.
2. **Ack**: сразу после получения агент отправляет `POST /commands/{id}/status`:
   ```json
   { "status": "in_progress", "message": "ack" }
   ```
3. **Heartbeat**: для длительных команд агент шлёт `POST /commands/{id}/status`:
   ```json
   { "status": "in_progress", "message": "heartbeat" }
   ```
   каждые **30 секунд**, пока команда выполняется.
4. **Результат**: после завершения агент отправляет `POST /commands/{id}/result`.
5. **Retry**: если результат не удалось доставить (не 2xx или сеть недоступна), агент сохраняет его локально и повторяет отправку каждые **10 секунд** из фонового потока.
6. **Startup replay**: при следующем запуске агент, прежде чем открыть новый long poll, отправляет все неотправленные результаты прошлой сессии.
7. **Timeout на стороне агента**: у каждой команды есть внутренний лимит выполнения. По умолчанию — **300 секунд**:
   - `pause`: `duration + 10` секунд, но не более 90000.
   - `hold_key`: `duration/1000 + 10` секунд, но не более 70.
   - `join_private_server`: 60 секунд.
   - При превышении агент принудительно отменяет выполнение и отправляет `status: "error"`.

## Что backend должен делать

1. **Принимать идемпотентно** `POST /commands/{id}/result` и `POST /commands/{id}/status`.
   - Рекомендуется хранить `id` уже обработанных результатов или проверять, что текущий статус команды не финальный, прежде чем обновлять его.
2. **Обновлять `updated_at` у команды при каждом `in_progress`** heartbeat/ack.
   - Это позволяет отличать живую команду от зависшей.
3. **Не выдавать повторно команду**, пока она в статусе `in_progress`.
   - Если агент не прислал ack в течение нескольких секунд после выдачи, backend может считать выдачу неудачной и вернуть команду в `pending`. Но после ack/heartbeat команда должна оставаться в работе у этого аккаунта.
4. **Отмечать зависшие команды как `declined`**.
   - Если от агента нет ack, heartbeat и результата дольше, чем выбранный серверный таймаут (например, 5 минут), backend может перевести команду в `declined` и выдать другому агенту.
   - Примечание: агентский таймаут по умолчанию — 300 секунд, поэтому серверный таймаут должен быть ≥ 5 минут, чтобы не конфликтовать.
5. **Возвращать 2xx на успешные и повторные приёмы результатов**, иначе агент будет пытаться отправить снова.
6. **Вести историю результатов**, если требуется аудит. Идемпотентность не означает отказа от логирования.

## Примеры последовательностей

### Успешная команда

```
GET /commands/next → 200 { id: 1, command_type: "move_x", ... }
POST /commands/1/status { status: "in_progress", message: "ack" } → 200
POST /commands/1/status { status: "in_progress", message: "heartbeat" } → 200   (через 30s)
POST /commands/1/result { result: "{\"success\":true}", status: "completed" } → 200
```

### Сетевой сбой при отправке результата

```
POST /commands/2/result { result: "...", status: "completed" } → 500 / timeout
... 10 секунд ...
POST /commands/2/result { result: "...", status: "completed" } → 200
```

Backend должен ответить 200 и не создать вторую запись результата.

### Зависшая команда

```
GET /commands/next → 200 { id: 3, command_type: "pause", payload: { duration: 1000 } }
POST /commands/3/status { status: "in_progress", message: "ack" } → 200
... нет heartbeat/result более 5 минут ...
Backend переводит команду 3 в declined
```

## Проверка

Backend считается совместимым, если:
- [ ] `GET /commands/next` возвращает одну команду и корректно обрабатывает long poll.
- [ ] `POST /commands/{id}/result` принимается и финализирует команду.
- [ ] Повторный `POST /commands/{id}/result` не создаёт дубликатов и возвращает 2xx.
- [ ] `POST /commands/{id}/status` с `in_progress` обновляет `updated_at` и не портит финальный статус.
- [ ] Команда не выдаётся повторно, пока она в `in_progress` и приходят heartbeat.
- [ ] После отсутствия heartbeat/result дольше серверного таймаута команда переходит в `declined`.
