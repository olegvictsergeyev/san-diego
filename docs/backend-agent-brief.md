# Краткий бриф для backend-агента: API команд San Diego

## Задача

Добавить к существующему сервису `http://195.161.68.193:5173/api` endpoint'ы для управления командами, которые выполняет внутриигровой Roblox-агент.

## Статус аккаунта

Агент отправляет `POST /game/update` при изменении состояния аккаунта (позиция, баланс, статус, текущая команда и т.д.), при старте агента, а также принудительно раз в 5 минут, если не было других отправок. Идентичные статусы повторно не отправляются.

Статусы аккаунта:
- `idle` — в игре, нет активной команды.
- `in_progress` — выполняет команду.
- `error` — произошла ошибка при выполнении команды.
- `offline` — аккаунт не в игре.

При статусах `in_progress` и `error` в `custom_data` передаются поля `current_command` и `command_started_at` (время по +03:00).

```json
{
  "nickname": "PlayerOne",
  "game_slug": "san-diego",
  "server_id": "abc-123-uuid",
  "place_id": "123456789",
  "status": "idle",
  "version": "1.0.0",
  "custom_data": {
    "position_x": 123.5,
    "position_y": 10.0,
    "position_z": -45.2,
    "team": "Civilian",
    "balance": 1250.50,
    "current_command": "move_x",
    "command_started_at": "2026-08-27T15:30:00+03:00"
  }
}
```

Tracked-поля для игры `san-diego`:
- `position_x`, `position_y`, `position_z` (number)
- `team` (string)
- `balance` (number)
- `current_command` (string)
- `command_started_at` (string)
- `district` (string) — район карты по `workspace.Map.Static.Locations`: `SanDiego` (город, x −1531…709), `Border` (погранполоса, x 2430…2775), `OldTown` (x 3486…7402); `unknown` — вне зон.
- `poi` (string) — ближайшая именованная точка из `workspace.Nodes.Waypoints` (Bank, GunStore, BlackMarket, ElCapo, Apartments, Docks, Warehouse, Gym, Petrol и др., ~24 шт.); пустая строка, если точки недоступны.
- `poi_dist` (number) — дистанция до ближайшего POI по XZ в стадах; `-1`, если недоступно.
- `agent_uptime_s` (number) — аптайм инстанса агента, сек.
- `mem_kb` (number) — память Luau (`gcinfo()`), КБ.
- `fps_avg_60s`, `fps_min_60s` (number) — средний и минимальный FPS за последнее окно 60 с; появляются после первой минуты работы.
- `http_fail_streak`, `http_total_fails` (number), `http_last_error` (string) — транспортные сбои HTTP-стека агента (таймауты/обрывы). Растущий стрик до молчания — маркер деградации сети/клиента.
- `prev_log_tail` (string) — разово при старте: хвост (до ~2000 символов) локального лога прошлой сессии. Постмортем жёстких зависаний: если клиент умер без дисконнект-сигнала, последние события прошлой сессии приходят при перезапуске.

## Переподключение после дисконнекта

Агент **не переподключается автоматически** после дисконнекта или другой системной ошибки. Вместо этого он отправляет `POST /game/update` с `status = "offline"` и информацией об ошибке в `custom_data.disconnect`:

```json
{
  "title": "Disconnected",
  "message": "You have been disconnected. (Error Code: 277)",
  "code": "277"
}
```

Всеми переходами между серверами управляет бэкенд через команды, например `join_private_server`. После успешного запуска агента старый `disconnect` сбрасывается и отправляется актуальный статус.

**Семантика `join_private_server` (с v2.12.2):** результат команды (`POST /commands/{id}/result`) приходит только ПОСЛЕ того, как агент стартовал на новом сервере и клиент стал готов принимать команды (персонаж загружен + пауза ~8 с). Пока идёт переход, агент на старом сервере не забирает новые команды из `GET /commands/next` — они остаются на бэкенде и будут приняты в работу уже на новом сервере. Поэтому по факту получения результата `join_private_server` бэкенд может сразу слать следующие команды. Если телепорт не состоялся (join отклонён/не начался), приходит результат со статусом `error` и причиной.

**Важно: статус `completed`/`error` команды `join_private_server` определяется ТОЛЬКО результатом агента (`POST /commands/{id}/result`).** Нельзя завершать команду по смене `job_id` в `POST /game/update`: первый апдейт с нового сервера приходит раньше готовности агента (до конца паузы ~8 с), и отправленная следом команда попадёт в окно, когда фетчер ещё не опрашивает бэкенд, — команда будет потеряна (утечёт в зависшее соединение и зависнет до `declined`). Кроме того, детект по `job_id` маскирует ошибки агента (например, отклонение `CanJoinServerByCode`, когда персонаж уже на целевом сервере — агент шлёт `error`, а детект перезапишет его `teleported`). Допустим только fallback: если результата от агента нет ~90 с, бэкенд может завершить команду по факту смены `job_id`.

### `GET /commands/next`

Long-poll. Query-параметры:
- `nickname` (обязательно)
- `long_poll=true` (обязательно)
- `timeout` (опционально) — максимальное время ожидания в секундах, 1..300, по умолчанию 30.

Поведение:
- Удерживать соединение до появления команды или таймаута.
- Возвращает одну команду в статусе `in_progress` с полем `taken_at`.
- Возвращает `null` при таймауте.
- После ответа агент сразу открывает новый long poll.

### `POST /commands/{id}/result`

Тело:
```json
{
  "result": "JSON-строка или текстовое описание результата",
  "status": "completed" | "error" | "cancelled"
}
```

Агент сохраняет результат локально и повторяет отправку, пока сервер не подтвердит приём. Сервер должен обрабатывать повторные запросы на один и тот же `id` идемпотентно.

### `POST /commands/{id}/status` (опционально)

Тело:
```json
{
  "status": "in_progress" | "completed" | "error" | "cancelled" | "declined",
  "message": "optional"
}
```

## Поддерживаемые команды

- `get_commands` — без параметров, возвращает список доступных команд.
- `move_x`, `move_y`, `move_z` — параметры `value` (number, -7000..7000) и `speed` (integer, 1..10, опционально, по умолчанию 10).
- `move_to` — параметры `x` (number, -7000..7000), `z` (number, -7000..7000) и `speed` (integer, 1..10, опционально, по умолчанию 10). Плавно перемещает персонажа к координатам X/Z с прилипанием к рельефу. При встрече стены: низкие препятствия (≤12 ст) перешагиваются с подъёмом; высокие — тангенциальный обход (боковые шаги вдоль препятствия по стороне со свободным пространством, возврат на курс при восстановлении прямого прохода; анти-зацикливание, бюджет детура до 800 ст/120 с). При невозможности обойти — остановка с `blocked: <объект> (avoid: <причина>)` и реальной позицией.
- `pause` — параметр `duration` (number, 0..86400).
- `respawn` — параметр `skip_in_spawn` (boolean, опционально) — `true` = не респавниться, если персонаж уже в зоне спавна (SpawnLocation его TeamColor или Neutral в пределах площадки + 12 ст): успех с `respawned=false`, `skipped=true`, `in_spawn=true`, `spawn=<имя>`. Без параметра (или не в зоне) — умирает и ждёт готовности: команда завершается только когда персонаж снова может выполнять команды (новый character, живой гуманоид, HumanoidRootPart, до 30 с, при таймауте — ошибка).
- `spawn_vehicle` — параметр `name` (string, 1..64) — имя техники как в списке спавнера (`ducati`, `C63DTM`, `911`). Заспавнить технику с ближайшей VehicleSpawner-площадки (в радиусе 50 ст от персонажа) без открытия панели: прямой вызов серверного ремоута `VehicleSpawnerService:SpawnVehicleFromSpawner`, сервер валидирует доступ/владение. При успехе персонаж садится в технику. Результат: `spawned`, `position`, `spawner_distance`.
- `transfer_money_via_respawn` — цикл: параметры `identifier`, `amount`, `max_attempts`, `wait_seconds`. Повторяет respawn, пока баланс цели не достигнет `amount`. Перед каждым respawn'ом агент преследует цель, чтобы деньги упали рядом. Если `max_attempts` исчерпаны раньше — ошибка `max attempts reached` с `data.partial=true`, `data.final_balance`, `data.target_amount`, `data.progress` (0..1). Это промежуточный результат (с v2.12.27): бэкенд перевыпускает ту же команду с тем же payload — агент продолжит с текущего баланса цели.
- `respawn_for_money` — одна итерация: параметры `identifier`, `amount`, `wait_seconds`. Проверяет баланс цели, преследует её, делает respawn, ждёт и возвращает `reached`, `before_balance`, `after_balance`, `respawned`.
- `get_inventory` — без параметров. Возвращает инвентарь: `held` (предмет в руке или null), `backpack` (словарь имён с количеством), `backpack_total`, `printers_backpack`, `printers_held`, `printers_total` и `printer_ids` (атрибут `PersistentToolId` каждого принтера).
- `buy_printer` — купить N Money Printer у витрины (`WorldBuyableItems`). Требует стоять у витрины. Покупка выполняется прямым вводом в ProximityPrompt (`InputHoldBegin`/`InputHoldEnd`, без эмуляции клавиш), каждая покупка верифицируется по приросту числа принтеров; при нехватке денег команда останавливается и возвращает `bought` — сколько успела купить. Параметр `count` (1..50, по умолчанию 1).
- `pickup_printer` — подобрать расставленные принтеры обратно в инвентарь (RemoteFunction `PickupMoneyPrinter` с экземпляром модели; подбор верифицируется по исчезновению модели). Работает только в своей комнате, нужен фильтр: либо `printer_id` (MoneyPrinterId модели), либо `floating=true` — только «плавающие» принтеры (дно выше пола комнаты > 1.5 ст, например вставшие на шкаф). Параметр `max_count` (1..50, по умолчанию 50). Результат: `picked`, `failed`, `inventory`, `room_total`.
- `pickup_all_printers` — подобрать ВСЕ расставленные принтеры апартамента (все комнаты), без параметров. Перед каждым подбором персонаж подводится к промпту и ждётся репликация позиции на сервер, неуспех повторяется до 3 раз — срабатывает даже если персонаж стоит на принтере. Результат: `picked`, `failed`, `inventory`, `room_total`.
- `deploy_printers` — проверить инвентарь и расстановку: если есть принтеры в рюкзаке/руке и разложено < 50 — подобрать все разложенные и разложить заново сеткой по комнате (ряды прижаты к стене напротив двери, шаг 1.4, валидация мебели рейкастами); затем встать по центру комнаты спиной к стене с дверью. Если принтеров нет — только встать по центру спиной к двери. Результат: `inventory`, `placed_before`, `redeployed`, `picked`, `placed`, `failed`, `cells`, `start_side`, `room_total`, `position`, `facing`, `door_side`.
- `rent_apartment` — параметр `apartment_id` (integer, 0..10000, опционально) — ApartmentId конкретного номера; `0` или отсутствует — ближайшая свободная парадная дверь. Арендовать номер отеля, если не арендован: прямой вызов `ApartmentService:PurchaseApartment` (тот же, что кнопка Purchase Apartment), без нажатия E. Персонаж должен стоять у двери (до 20 ст). Если `OwnedApartmentId` у игрока уже есть — покупка не выполняется, возвращается `already_rented`. Требует команду Civilian. Результат: `rented`, `already_rented`, `apartment_id`, `door_distance`.
- `open_door` — открыть дверь номера без нажатия E: прямой вызов `ApartmentService:ToggleApartmentDoor` (тот же, что кнопка Open Door). Если дверь уже открыта — no-op, успех с `open=true`. Ближайшая доступная дверь (своя парадная или любая Interior, до 20 ст). Результат: `open`, `toggled`, `apartment_id`, `door_kind`, `door_distance`.
- `close_door` — закрыть дверь номера: аналогично `open_door`, но закрывает; если уже закрыта — no-op, успех с `open=false`.
- `fly_car` — полёт машины: поднять и держать на высоте, пока не придёт отмена. Параметр `height` (обязательный, integer 0..10) — градация высоты: 1 ≈ 1 ст над поверхностью (рейкаст вниз), 10 = +10 ст — максимум, разрешённый анти-читом в движении (выше +10 ст в движении сервер сбрасывает машину каждые ~13-15 с; абсолютный потолок ~64). `height=0` — быстрая посадка (свободное падение + короткий тормоз) и завершение сессии. Машина держится стабильно на месте (P-регуляторы позиции и ориентации). Требует сидеть в машине (сетевое владение физикой у клиента). Результат: `height`, `studs` (или `landed`, `knocks` при посадке).
- `nav_car` — перемещение летающей машины: параметры `x`, `z` (обязательные, integer −2000..2000) — смещение в стадах со знаком направления. По оси Y машина НЕ смещается: летит на текущей высоте (при активной сессии `fly_car` — на её высоте, иначе на текущей над поверхностью), повторяя рельеф по рейкасту. Скорость фиксированная 20 ст/с (25 ст/с на больших высотах накапливает срабатывания анти-чита; сбросы не смертельны — контроллер восстанавливается). Прерывается командой `cancel`: движение остановится, при активной сессии `fly_car` машина останется висеть на месте, иначе сессия завершится. Если была активна сессия `fly_car` — после прибытия машина вернётся в зависание на прежней высоте. Требует сидеть в машине. Результат: `travelled`, `knocks`, `landed`/`resumed`, `height`.
- `drive` — наземная езда (мотоцикл/машина). Управление рулением: техника разворачивается носом к курсу (AlignOrientation) и тянется только вдоль продольной оси — z корректируется поворотами руля, бокового скольжения нет; если техника стоит боком — сначала развернётся, потом поедет. Параметр `x` (необязательный, integer −20000..20000, по умолчанию 0) — смещение по X со знаком. Торможение резкое (реальное замедление ~65 ст/с²) с точной остановкой у цели. Параметр `z` (необязательный, number, по умолчанию 150.07 — главный проспект San Diego) — абсолютная координата полосы: если не передан, транспорт рулит на полосу и придерживается её всю дистанцию. Если `x` = 0/отсутствует — только встать в полосу `z`, не уезжая. Параметр `speed` (необязательный, integer 0..10, по умолчанию 10) — ограничение скорости по линейной шкале 0..360 ст/с (с 2026-09-11; античит стал обнулять скорость уже на ~405 ст/с, шкала пересчитана «порог − 10% = уровень 10», v2.12.30): 10 = полная скорость, 0 = не уезжать, только встать в полосу. Таймаут масштабируется от заданной скорости (длинные дистанции на малой скорости не обрываются). Детект препятствий (невидимые стены NavBlockers) вдоль оси дороги; при встрече полоса смещается (±14..±42), при отсутствии свободной полосы — торможение и ошибка `blocked`; пока транспорт далеко от полосы (выравнивание) детект не работает. Параметр `jump_off` (необязательный, boolean, по умолчанию false) — true = не тормозить: по достижении цели персонаж спрыгивает с транспорта, техника с сохранением скорости катится дальше сама (в результате `jumped=true`, `jump_speed`, `brake_dist=-1`). Параметр `tolerance` (необязательный, number 1..1000, по умолчанию 40) — допуск прибытия по X: |факт − цель| > tolerance = ошибка `missed target by N studs` (в результате `overshoot`, `tolerance`). В конце — выпрямление по оси дороги и активная остановка (техника иначе сохраняет импульс и катится сама).  Прерывается командой `cancel` (торможение и остановка). Параметр `probe` (необязательный, boolean, с v2.12.29) — режим замера порога античита: едет с нарастающим капом скорости (+10 ст/с каждые 2 с, с 150 ст/с) до срабатывания игрового WarningGui; в результате `probe_triggered` и `probe_threshold` (кап на момент срабатывания). Замер намеренно провоцирует инфракцию — только по решению владельца. Требует сидеть в транспорте. Результат: `travelled`, `vmax`, `target_vmax`, `brake_dist`, `lane_z`, `time`, опционально `t_300` (время разгона до 300 ст/с). Ошибки: `blocked: <объект>`, `knock at v=<скорость>`, `stuck/locked` (сторож застревания сильно ослаблен: только в фазе разгона/крейсера, только пока цель не пройдена, окно 4 с — перелёт цели с медленным торможением, типичный для байка, ошибкой не считается). При ошибке с накопленными данными `result` — JSON `{ "error": "...", "data": { ... } }`.
- `jump` — без параметров, заставляет персонажа подпрыгнуть.
- `hold_key` — параметры `key` (`string`, 1..32, имя клавиши из `Enum.KeyCode`, например `"E"`) и `duration` (`integer`, 0..60000, миллисекунды). Нажимает клавишу, удерживает указанное время, затем отпускает. `duration = 0` — нажать и сразу отпустить.
- `join_private_server` — параметр `code` (string, 1..64).
- `cancel` — без параметров, отменяет текущую команду.
- `update_agent` — обновляет агента до актуальной версии: штатная остановка и перезапуск загрузчика с GitHub. Опциональный параметр `delay` (integer, 0..300, по умолчанию 5) — задержка перед перезапуском. Команда возвращается немедленно со статусом `scheduled`; аккаунт ненадолго уходит в offline и возвращается после перезапуска. Позволяет обновить агента на конкретном аккаунте без перезахода в игру.
- `afk` — параметры `enabled` (`string`, `"on"`/`"off"`, опционально) и `interval` (`integer`, 60..3600, опционально). Управляет периодическим незаметным действием, предотвращающим кик за бездействие. По умолчанию включено, интервал 300 секунд.
- `set_action` — параметры `action` (`string`, 0..32) и `except` (`string`, 0..256, опционально). Устанавливает `custom_data.action` (статус действия аккаунта, например `"farm"`) без выполнения игровых действий. Пустая строка `action` сбрасывает значение. Любая другая команда сбрасывает `action`, если её имя не указано в `except` (список через запятую, пробелы игнорируются). Дисконнект/ошибка и перезаход на сервер тоже сбрасывают `action`.
- `set_time` — параметры `name` (`string`, одно из `time_1`..`time_5`) и `value` (`integer`, Unix timestamp, опционально). Устанавливает указанный таймер в `value` или в текущее время. После респавна `time_2` автоматически сбрасывается.
- `get_server_players` — без параметров. Возвращает массив объектов по всем игрокам на текущем сервере: `roblox_name`, `display_name`, `user_id`, `team`, `balance`, `properties` (`beach_houses`, `apartments`) и `money_printers` (только для LocalPlayer).
- `get_player` — параметр `identifier` (`string`, 1..64). Возвращает объект с данными об одном игроке. `identifier` может быть `roblox_name`, `display_name` или `user_id`.
- `set_team` — параметр `team` (`string`, 1..32). Ищет команду в `Teams` по имени и устанавливает `LocalPlayer.Team`.
- `turn` — параметры `degrees` (integer, 0..360) и `speed` (integer, 1..10, опционально, по умолчанию 10). Плавно поворачивает персонажа на абсолютный угол.
- `turn_with_camera` — параметры `degrees` (integer, 0..360) и `speed` (integer, 0..10, опционально, по умолчанию 10). Поворачивает персонажа и камеру. Меньший `speed` делает поворот медленнее и увеличивает время удержания камеры после поворота, чтобы Roblox-камера успела подхватить новое направление. `speed=0` — ничего не делать: ни персонаж, ни камера не поворачиваются (успешный no-op, возвращает `noRotation: true`).
- `tilt_camera` — параметры `degrees` (integer, -80..80) и `speed` (integer, 1..10, опционально, по умолчанию 10). Наклоняет только камеру по вертикали, не поворачивая персонажа. `0` — горизонт, положительные значения — вверх, отрицательные — вниз.

## Надёжная доставка результатов

1. После получения команды агент отправляет `POST /commands/{id}/status` со статусом `in_progress` (ack).
2. На время выполнения длительных команд агент шлёт heartbeat `POST /commands/{id}/status` со статусом `in_progress` каждые 30 секунд.
3. По завершении агент сохраняет результат в локальный файл `pending-results-{nickname}.json` и сразу пытается отправить `POST /commands/{id}/result`. При неудаче повторяет попытку каждые 10 секунд.
4. При старте агента, перед началом нового long poll, все неотправленные результаты предыдущей сессии отправляются повторно.
5. У каждой команды есть внутренний таймаут выполнения (по умолчанию 300 секунд; для `pause`/`hold_key` — `duration + запас`; для `join_private_server` — 60 секунд). При зависании агент принудительно отменяет команду и отправляет статус `error`.
6. Сервер должен быть готов к повторным `POST /commands/{id}/result` и `POST /commands/{id}/status` без побочных эффектов (идемпотентность).

## Жизненный цикл команды

1. Агент открывает long poll `GET /commands/next`.
2. Сервер выдаёт команду в статусе `in_progress` с полем `taken_at`.
3. Агент подтверждает получение через `POST /commands/{id}/status` (`in_progress`) **сразу при получении команды из long poll, ДО начала её исполнения** (с v2.12.22; раньше ack шёл только со старта исполнения — reaper отклонял команды, ожидавшие в очереди за длительной командой). При необходимости шлёт heartbeat каждые 30 секунд.
4. Агент выполняет команду. **Команда `respawn` (с v2.12.22) прерывает текущую команду** (аналогично `cancel`) и исполняется немедленно — бэкенд может слать её как аварийную в любой момент, в т.ч. пока выполняется другая команда. Кроме того, агент сам детектирует падение персонажа под карту (y < −120) и делает аварийный респавн без команды.
5. Агент отправляет `POST /commands/{id}/result` с `result` (строка) и `status`. При сетевом сбое повторяет отправку.
6. Если от агента не поступал результат или heartbeat дольше внутреннего таймаута команды (по умолчанию 5 минут), сервер может перевести команду в `declined`.
7. При необходимости агент отправляет `POST /commands/{id}/status` (например, для отмены).

## Отмена

Команда `cancel`:
1. Прерывает текущую команду.
2. Текущая команда получает статус `cancelled`.
3. Сама команда `cancel` завершается статусом `completed`.

## Требования

- Одна команда в работе у одного аккаунта одновременно.
- Атомарная выдача `pending`-команд.
- Сохранение истории/результатов команд.
- OpenAPI/Swagger-документация.
- Стек и структура — как у существующего сервиса.
